# 04. ベンチマーク方法

本手法の評価は 2 段構えで行う。

- **A. 論文規模の評価**: 実際の事前学習骨格と人手の聴取。論文と同じ設計。
- **B. トイ評価**: CPU だけで回せ、完全に自動化した評価。本リポジトリで実行済み。

## A. 論文規模の評価（実骨格向けの手順）

### A.1 何を測るか

論文の主張は「**未知の難読語**で、タグを使うと**指定したアクセント**どおりに発音される割合が、プレーンなカナより大きく上がる」というもの（Sarashina2.2-TTS で 0.89 対 0.57、4 種の骨格で 0.80〜0.93 対 0.38〜0.60）。

| 指標 | 内容 | 手段 |
|---|---|---|
| **アクセント正解率**（主指標） | 聴取者が「指定どおりのアクセント」と判断した割合 | スクリーニングした母語話者の聴取試験。評定者間の一致度は Fleiss κ で報告する（論文 0.85） |
| 読み正解率 | 語の読みが指定どおりか | 聴取、または日本語 ASR（kotoba-whisper、ReazonSpeech）でカナ化した CER |
| 自然さ | タグを入れても音質・自然さが落ちないか | UTMOS / UTMOSv2、MOS |
| 話者類似度 | adapter で声質が変わらないか | 話者埋め込み（ERes2Net / ECAPA）のコサイン類似度。比較対象は「adapter なしの同じ文」 |
| 副作用 | タグのない文で出力が変わらないか | adapter の有無で生成し、CER・UTMOS の差を見る |

### A.2 評価セット

- **難読語セット**: 骨格が誤読しやすい語（固有名詞、難読漢字、専門用語）を 50 語以上。UtterTune の `data/eval/difficult_50.tsv`（MIT）は「vanilla / kana / tag」の 3 条件の文を含むので、そのまま使える。
- **アクセント掃引**: 各語について、辞書のアクセント型だけでなく **0〜n 型すべて**をタグで指定する。「辞書を再現した」のではなく「指定に従った」ことを確かめるため。
- **一般語セット**: 蒸留に使った語と使っていない一般語。副作用の確認に使う。

### A.3 条件と比較

| 条件 | 入力 | モデル |
|---|---|---|
| raw | 漢字のまま | 骨格 |
| kana | 語をカタカナに置換 | 骨格 |
| UtterTune | タグ | 骨格 ＋ UtterTune の LoRA（録音で学習） |
| **自己蒸留** | タグ | 骨格 ＋ 本手法の adapter |

- 統計: 条件間の正解率の差は、同じ語の対応のある比較なので McNemar 検定にかける。95% CI はブートストラップで出す。
- 聴取試験: 刺激の順序をランダムにし、条件を隠す。アクセント型の図（高低の線）を提示して判定させる。

## B. トイ評価（本リポジトリで実行可能）

### B.1 設計

聴取者の代わりに、**オラクル（HTS）による強制選択**を使う。

1. 評価文ごとに、対象語のアクセント型を 0〜n すべてに書き換えた参照音声を HTS で合成する（`OracleRenderer.render_with_override`）。読みは辞書どおり、文の他の部分は同一。
2. 生成音声（mel → Griffin-Lim → WORLD Harvest）と各参照（**同じ** mel → Griffin-Lim → Harvest の経路）を mel 上の DTW で整列する。
3. **参照同士で log-F0 が食い違うフレーム**（対象語、続く助詞、アクセントによるダウンステップの範囲）だけで、中央値を除いた log-F0 の平均絶対差を計算する。
4. 最も近い参照のアクセント型を「聞こえたアクセント」とし、指定と一致すれば正解とする。

補助指標の `mel_dist` は、指定アクセントの参照との DTW 後の log-mel L1 距離。読みの崩れの目安になる。

### B.2 判定器自身の検証（`validate-judge`）

判定器が当てにならなければ、ベンチマークの数値に意味はない。そこで HTS の音声を**テンポ 1.1 倍・ピッチ +1 半音**に変えて合成し、元の参照の中から正しいアクセント型を選べるかを測る（`scripts/benchmark.py validate-judge`）。

- 結果は [05_results.md](05_results.md) §2 にある。この数値が、ベンチマークで識別できる上限の目安になる。
- **平板型（0）と尾高型（n）**は、後続の助詞の高さでしか区別できない。「〜の」の前ではほぼ同じに実現される（中和）。
  - 既定では「の」が続く評価文を除外する。
  - 平板型と尾高型を同一視した緩い正解率（`accent_acc_lenient`）も併記する。

開発時の比較（16 文 × 全アクセント型 = 65 判定、テンポ・ピッチ変化あり）:

| 判定方式 | 正解率 |
|---|---|
| 発話全体の log-F0 距離、参照はきれいな波形 | 0.71 |
| 発話全体の log-F0 距離、参照も Griffin-Lim 経由 | 0.75 |
| **参照間で食い違う領域だけ**、参照も Griffin-Lim 経由（採用） | **0.88** |

### B.3 条件

| 条件 | 入力 | モデル | 期待 |
|---|---|---|---|
| raw | 漢字（骨格は一度も見ていない文字） | 骨格 | 読めない。下限 |
| kana | カタカナ | 骨格 | 読めるが、アクセントは骨格の推測（論文の kana 条件に相当） |
| tag | タグ（辞書のアクセント） | 骨格 ＋ adapter | 読み・アクセントとも正しい |
| tag_sweep | タグ（0〜n 型すべて） | 骨格 ＋ adapter | 指定したアクセント型になる（制御性） |
| raw_adapted（任意） | 漢字 | 骨格 ＋ adapter | タグのない入力に副作用がない |

偶然の正解率は 1 / (n + 1) で、語のモーラ数によって 0.17〜0.5 になる。

### B.4 実行

```bash
uv run python -m scripts.benchmark validate-judge --items data/toy/eval_difficult.jsonl --out results/judge_validation.json
uv run python -m scripts.benchmark run --backbone exp/backbone/model.pt --adapter exp/adapter/adapter.pt \
    --items data/toy/eval_difficult.jsonl --out results/benchmark_difficult.json
uv run python -m scripts.benchmark run --backbone exp/backbone/model.pt --adapter exp/adapter/adapter.pt \
    --items data/toy/eval_common.jsonl --conditions raw,tag,raw_adapted --out results/benchmark_common.json
```

出力は JSON（全判定の記録と集計）と Markdown の表。各条件のアクセント正解率（厳密・緩い）、ブートストラップ 95% CI、mel_dist、アクセント型別の内訳を含む。

### B.5 トイ評価の限界

- 骨格も参照も同じ HTS の声で、学習データも HTS で合成している。実音声の多様さ（話者・韻律の揺れ）はない。
- 「未知語」は文字ごと未知（`<unk>`）なので、raw 条件は実骨格より極端に悪い。比較の主眼は kana と tag の差にある。
- 判定器は F0 の形だけを見る。読みの正しさは mel_dist による間接的な確認にとどまる。
- 以上の理由から、トイ評価の数値を論文の数値と直接比べることはできない。トイ評価で確かめているのは、パイプラインが機能すること（タグで指定したアクセントが出力に反映されること）である。
